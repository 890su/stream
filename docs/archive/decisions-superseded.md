## 2026-11-11 — Комплект развёртывания шага 1 через пользовательский systemd

**What** — Подготовлены пользовательские units `stream.service`, `stream-backup.service` и
`stream-backup.timer`. Ночная копия через `VACUUM INTO` включает базу и медиа, на которые ссылается снимок.
Копии сохраняются в датированных каталогах `~/backups/stream`.

**Why** — Node 24 запускает сервер напрямую. systemd поддерживает перезапуск и ночной таймер.
Тест восстановления проверяет согласованность базы и медиа.

**Boundary** — Выкладку и маршрут существующего Cloudflare Tunnel применяет владелец по `deploy/DEPLOY.md`.
Проверки Android и неделя использования остаются открытыми. Хранение и перенос резервных копий контролирует владелец.

**Affected** — `deploy/`, `src/backup.ts`, `src/store/store.ts`, `PLAN.md`.

## 2026-11-11 — Темы в ленте: фоновая обводка и окно истории темы
> Заменено 2026-11-14: тема — строка темы над сообщением и свой экран («Касание — панель, долгое нажатие —
> выделение»); связанные сообщения — одним пузырём.

**What:** Сообщения одной темы объединены лёгкой общей фоновой обводкой. Переход по теме — окно с историей
только этой темы, листается прокруткой. Смахивание по сообщению для этого не используется.
**Why:** Решение владельца: окно интуитивнее смахивания и не конфликтует с жестом переключения панелей.
**Affected:** `CONCEPT.md` §5, `web/feed.js`

## 2026-11-17 — Звонки в журнале: источник `android_calls`, проба через приложение автоматизации
**What:** Входящие, исходящие и пропущенные звонки — события `kind: call` (`source: android_calls`,
`payload.data.call`: направление, номер, имя, начало, длительность). Описание звонка — обычное сообщение-
продолжение звонка. Приём — отдельный адрес `POST /api/calls` (и `/api/calls/:id/note`) с токеном, который
умеет только это; id звонка сервер строит из номера и времени. Сначала проба через Tasker или MacroDroid на
телефоне, свой компаньон на Kotlin — если описание звонков приживётся.
**Why:** Владелец хочет помечать звонки в журнале и записывать, о чём был разговор. PWA журнал вызовов не видит;
приложение автоматизации даёт проверить привычку за вечер настройки, без сборки и установки своего APK.
**Boundary:** Event v1 получает новое значение `kind` — добавление, без новой версии контракта. Токен
владельца в приложение автоматизации не кладётся. Номера и имена — только в базе (правило 15). Запись разговора
не делаем (§10). Направление и длительность из приложений автоматизации бывают ненадёжны — поля необязательные.
**Affected:** `CONCEPT.md` §8.1, `contracts/event.schema.json`, `src/server/`, `web/`, `docs/plans/2026-11-17-calls-trial.md`

## 2026-11-17 — Telegram: шлюз на каждый аккаунт через клиентский API, вместо бота с бизнес-подключением
> **Заменено** решением 2026-11-17 «Telegram официально: бизнес-бот на каждый аккаунт…».
**What:** Аккаунты Telegram BY и PL подключаются каждый своим шлюзом — процессом в своём контейнере на srv-150,
вошедшим как ещё одно устройство владельца (официальный клиентский API, MTProto). Шлюз пишет сообщения в Stream
через свои адреса с отдельным токеном (по образцу `/api/phone`), забирает одобренные действия `send_message` и
возвращает результат. Сообщения — обычные `text` / `voice` / `photo` / `file` с `source: telegram` и
`payload.data.telegram`; id — из аккаунта, чата и номера сообщения.
**Why:** Владельцу нужны группы (в них заявки), переписка с компаньонами и подрядчиками и свои сообщения,
написанные в самом Telegram. Бот с бизнес-подключением этого не видит, требует Premium и отвечает только в окне
24 часа. n8n и боты не работают как пользовательский аккаунт.
**Boundary:** Отступление от правила 10 («один процесс»): шлюз — отдельный процесс ради изоляции учётных данных
каждого аккаунта; сервер и база остаются одни. Код входа и пароль 2FA вводит только владелец; сессия — секрет
на сервере. Шлюз «слеп» (правило 6): ленту не читает, ИИ не вызывает. Секретные чаты недоступны. Заменяет
пункт «Telegram-секретарь (бизнес-подключение)» в §7.
**Affected:** `CONCEPT.md` §8.2, §7, `registry/connectors.yaml`, `docs/plans/2026-11-17-p11-telegram.md`

## 2026-11-17 — Шлюз Telegram на Telethon (Python), не на GramJS
> **Заменено** решением 2026-11-17 «Telegram официально: бизнес-бот на каждый аккаунт…».
**What:** Шлюз аккаунта — `gateway/telegram/` на Telethon 1.45 в своём контейнере (образ `python:3.13-slim`).
Сервер Stream остаётся на Node без зависимостей. Ответы шлёт сырой `messages.sendMessage` с `random_id` из id
действия: повтор не создаёт второе сообщение и на стороне Telegram.
**Why:** GramJS (`telegram` в npm) помечен как архивный, разработка ушла в молодой форк. Telethon — зрелый и
поддерживаемый; шлюз и так отдельный процесс, поэтому другой язык не усложняет сервер.
**Boundary:** Шлюз не получает токен владельца — только свой токен и `api_id`. Правка в Telegram — правка поверх
исходника; удаление не помечается (Telegram не сообщает чат удалённого личного сообщения).
**Affected:** `gateway/telegram/`, `deploy/docker-compose.yml`, `deploy/install.sh`, `docs/plans/2026-11-17-p11-telegram.md`
