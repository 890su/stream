# П14. Беседы и задачи: управление, процессы, бот, синхронизация — проект

> Статус: **проект на согласовании** (2026-11-18; вопросы проверяющего разобраны). После утверждения: правка `CONCEPT.md` (§2.3, §2.5, §2.8, §2.9, §5),
> запись в `decisions.md` (отменяет «тема = дело = задача» от 2026-11-18), затем план каждого этапа.

## 1. Зачем

Задачи теряются: обещал в чате «сделаю завтра» — и забыл; поручил напарнику — и не проверил; клиент ждёт ответа —
а сообщение утонуло в ленте. Лучшее, что уже есть, — ИИ читает переписку и сам заводит задачи. Нужно довести это
до управления: у задачи есть ответственный и исполнитель, поручённое контролируется, зависшее само напоминает о
себе, а сделанное попадает в учёт. Владелец работает в Stream, напарники — через бота; Google и Планфикс видят
те же задачи.

Прежняя попытка свести тему, дело и задачу в одну сущность отменяется: беседа и задача — разные вещи, связанные
сообщениями.

## 2. Цели, не-цели, анти-цели

**Цели**
- Главный экран — список бесед, как в Telegram, отсортированный по тому, кто кого ждёт.
- Задачи заводятся из переписки сами (как сейчас), включая обещания — свои и чужие — со сроком.
- Задача с ролями: ответственный, исполнители, контролёр, наблюдатели, постановщик, контрагент.
- Принять / поручить / отложить / готово — одним касанием; поручённое — под контролем.
- Процессы над задачами (напоминания, вопросы, подъём беседы) — правила-данные в реестре.
- Бот задач: владелец и напарники получают поручения, принимают, отчитываются, получают напоминания.
- Синхронизация: Google Задачи, Google Календарь, Планфикс — зеркала Stream (вариант А).
- Лента остаётся как вид для анализа и фильтров (ИИ, отчёты, поиск).

**Не-цели (сейчас)**
- Канбан и дашборды — позже; они будут читать сохранённые фильтры (§5).
- Метки с зависимыми параметрами («заявка» + «удалёнка» → длительность, результат) — отдельный этап 5; здесь
  только место для них в модели.
- Склейка бесед одного человека из разных каналов — с справочником контактов (П7).
- Совместная работа в самом Stream: напарники в приложение не входят, только бот.

**Анти-цели — провал, даже если работает**
- Напоминания превращаются в спам, который хочется выключить.
- Что-то уходит людям без «да» владельца (кроме того, что владелец сам разрешил правилом).
- Задача потерялась: была в переписке, но не стала задачей и никто не спросил.
- Stream превращается в ещё один Планфикс, который надо вести руками.

## 3. Ограничения

- Правила проекта (`CONTEXT.md`): журнал неизменяем, производное пересчитываемо, данные вместо кода, коннектор
  слеп, идемпотентность, один процесс и одна база, содержание не в git.
- Задача — проекция журнала (`task_change`); новая форма изменения задачи — новая версия контракта и запись в
  `decisions.md`. Старые события читаются и дальше.
- Google Задачи: у задачи нет исполнителя, срок — только дата (время API не хранит). Поэтому туда — только задачи,
  где исполнитель владелец; всё со временем — в Календарь. Проверить по документации при плане этапа 6.
- Google: вход OAuth владельца, своё приложение в Google Cloud — создаёт и подтверждает владелец.
- Планфикс: REST API только на платном тарифе — ❓ тариф владельца неизвестен; этап 7 зависит от этого.
- Telegram: бот может написать человеку только после того, как тот сам открыл бота (`/start`).

## 5. Модель

### 5.1 Лента
Журнал всех событий, как сейчас. Вид «Лента» — для анализа: фильтры по меткам, источникам, людям, датам; позже —
выборка для ИИ-аналитика (`CONCEPT.md` §9). Не главный экран.

### 5.2 Беседа
Чат с одним или несколькими людьми. Проекция журнала, отдельных событий не имеет.
- Ключ — канал: личный чат или группа Telegram (по аккаунту), номер телефона (звонки и SMS), чат с ботом задач,
  своя беседа «Я» (заметки себе, команды ИИ). С П7 беседы одного человека из разных каналов склеиваются.
- Участники беседы — люди без ролей; роли — у задач.
- **Состояние беседы** — вычисляется, пороги — данные (`registry/conversations.json`):

| Состояние | Когда |
|---|---|
| срочно | у связанной открытой задачи срок сегодня или просрочен, или метка срочности |
| ждёт меня | последнее сообщение входящее и без ответа, или связанная задача требует моего действия (новая, мне на проверку) |
| жду их | последнее сообщение моё, или связанная задача ждёт кого-то из участников |
| тихо | ничего из выше, есть открытые задачи или переписка моложе `quiet_days` |
| завершено | все связанные задачи закрыты, входящих без ответа нет `quiet_days` дней |

  Порядок списка: срочно → ждёт меня → жду их (внутри — от свежих к старым) → тихо → завершено (свёрнуто).
- В строке беседы: название, последнее сообщение, значок канала, число открытых задач и состояние.
- Внутри беседы: переписка всех её каналов, сверху — плашки связанных задач (статус, исполнитель, срок);
  ответ уходит выбранным каналом (строка «кому», `CONCEPT.md` §2.9), у каждого сообщения видно кому, куда, когда.

### 5.3 Задача

**Связь с беседами** — через сообщения: задача ссылается на сообщения (`add` / `remove`, как сейчас), беседы
задачи — беседы этих сообщений. Одна беседа — несколько задач; одна задача — несколько бесед (заявка клиента +
поручение напарнику).

**Стороны.** Ссылка на сторону: `me`, `ai`, `system`, `tg:<user id>` (человек в Telegram), `tel:<+цифры>`
(человек по номеру), `group:tg:<chat id>` (команда — группа Telegram), `name:<как назвали>` (человек, известный
только по имени, до справочника П7). Один пользователь Telegram — одна сторона во всех аккаунтах (BY, PL) и в
боте задач: id у него один. П7 сведёт `tg:`, `tel:` и `name:` одного человека в одну запись.

**Роли** (все необязательны, кроме ответственного):

| Роль | Кто | По умолчанию |
|---|---|---|
| постановщик | кто попросил | автор сообщения, из которого задача; моё обещание — я |
| ответственный | кто отвечает за итог | я, если задача пришла ко мне; иначе — кого просят в переписке |
| исполнители | кто делает (несколько) | пусто, пока не принято или не поручено |
| контролёр | кто проверяет | ответственный, если исполнитель — не он |
| наблюдатели | кто в курсе | участники беседы, кому я переслал |
| контрагент | организация | организация постановщика (с П7) или выбор из списка |

**Задачи без меня** (решение владельца 2026-11-18): разбор заводит задачи из всех отслеживаемых чатов, в том
числе где меня нет ни в одной роли — клиент просит напарника, напарник — другого напарника. Ответственный и
исполнитель — те, кто в переписке; я — наблюдатель. Такие задачи видны фильтром «Команда», не попадают в «Мои»,
не делают беседу «ждёт меня» и не шлют мне напоминаний; процессы для них — отдельные правила (например, «поручено
в группе и никто не принял за `ack_h`» → в сводку).

**Статусы:** `inbox` (новая, ждёт решения) → `todo` (принята, к выполнению) → `doing` → `waiting` (жду кого-то или
чего-то: `waiting_for` — сторона и срок) → `review` (исполнитель отчитался, ждёт проверки) → `done`; отдельно
`deferred` (отложена до даты) и `cancelled`. «Учтено» — не статус, а фильтр: `done` и в отчёте нет пропусков.

**Даты:** `due` (срок, дата или дата-время), `plan` (начало и длительность — для Календаря), `remind_at`.

**Обещание:** `promise` — кто обещал (`by`), к какому сроку, цитата-сообщение. Из «сделаю завтра» — задача мне со
сроком; из чужого «скину адрес вечером» — задача `waiting` с `waiting_for` = этот человек.

**Отчёт** — как сейчас (`report`, поля из реестра); с этапа 5 набор полей зависит от меток задачи.

**Внешние копии:** `external_refs` — id в Google Задачах, событие Календаря, задача Планфикса, с версией сверки.

**Переходы одним касанием** (в Stream и в боте):

| Действие | Что меняется |
|---|---|
| Принять | исполнитель = я, `todo` |
| Поручить… | исполнитель = человек / команда / ИИ, контролёр = я; черновик поручения в беседу или бот — уходит после «да»; `inbox`/`todo` до «принял» |
| Принял (исполнитель) | `todo` у исполнителя |
| Отложить до… | `deferred`, `remind_at` = дата |
| Жду… | `waiting`, `waiting_for` |
| Готово (исполнитель — не я) | `review`, мне задача на проверку |
| Готово (исполнитель — я) / Проверил | карточка «Задача выполнена?» с отчётом → `done` |
| Срок | сегодня / завтра / на неделе / дата |

Те же действия — текстом и голосом в беседе «Я»: «перенеси звонок Анне на пятницу» — разбор меняет задачу.

### 5.4 Сохранённые фильтры
Фильтр — набор условий по полям задачи (и состоянию беседы): поле, операция, значение; «и» / «или». Системные —
`registry/filters.json`: «Мои на сегодня», «Новые», «На контроле» (ответственный — я, исполнитель — не я, открыта),
«Жду от людей», «Просрочено», «На проверке», «Не учтено». Свои владелец сохраняет из левой панели — событием.
Список задач, будущий канбан, утренние три дела, правила процессов и зеркала синхронизации выбирают задачи
одними и теми же фильтрами.

### 5.5 Процессы
Правило — данные (`registry/processes.json`): **фильтр** + **таймер** от поля (`updated_at`, `due`,
`waiting_for.since`, последнее входящее) + **действие**:

| Действие | Что делает |
|---|---|
| напомнить мне | сообщение от бота задач владельцу (и служебное событие в ленте) |
| спросить меня | вопрос с кнопками и готовым черновиком людям (класс B) |
| поднять беседу | беседа — в «срочно» |
| в сводку | пункт утренней или вечерней сводки (шаг 6) |

Стартовый набор:
1. Обещал (я) и нет движения до срока «скоро» (`soon_h`) → напомнить мне; просрочено → утренние три дела.
2. Поручил, «принял» нет `ack_h` часов → спросить меня «Напомнить исполнителю?» с черновиком.
3. Жду от человека дольше `wait_days` → спросить меня «Напомнить?» с черновиком.
4. Входящее без ответа `reply_h` часов → поднять беседу.
5. `review` → задача мне «проверить».
6. `done` с пропусками в отчёте → вечерняя сводка.
7. Открытая задача без событий `stale_days` → недельный обзор: закрыть, отложить, следующий шаг?
8. Через 2 дня после закрытой заявки → черновик «всё работает?» клиенту (`CONCEPT.md` §7).

**Против спама:** у правила — повтор не чаще `every`, не больше N напоминаний в день на всё, тихие часы;
ответ «не сейчас» — отложить правило для задачи. Каждое срабатывание — событие с ключом (правило + задача +
период): повтор не шлёт второе. Сообщение людям без «да» — только для правила, которое владелец сам перевёл в
автоматический режим (по правилу `CONCEPT.md` §3.1: 20 подтверждений подряд без правок).

### 5.6 Бот задач
Отдельный бот «Stream задачи» (третий токен в `.env`), не бизнес-боты BY/PL: бизнес-бот пишет от имени аккаунта и
связан окном 24 часа, а у бота задач своя переписка с каждым, кто его открыл.
- **Владелец:** привязывается кодом с экрана «Система»; получает напоминания и вопросы процессов с кнопками;
  может принимать, переносить, закрывать задачи и писать в «Я» прямо из бота.
- **Напарник:** открывает бота по ссылке-приглашению владельца → запись «человек». Поручение приходит карточкой:
  что, срок, откуда (цитата заявки) и кнопки «Принять» / «Не могу». «Готово» → бот спрашивает поля отчёта по
  шаблону → задача уходит владельцу на проверку. Вопросы и ответы в боте — тоже беседа с этим человеком.
- **Команда:** поручение группе (группа Telegram с ботом или список людей) — первый «Принять» становится исполнителем.
- Бот — источник (нажатия и ответы — события с `author` — сторона `tg:<user id>`) и коннектор (отправка поручений и
  напоминаний — действия с ключом идемпотентности).

### 5.7 Синхронизация (зеркала)
Какие задачи куда уходят — фильтры в реестре, не код:
- **Google Задачи:** исполнитель — я, открытые; название, срок-дата, заметка со ссылкой на Stream. Обратно:
  «выполнено», срок, название.
- **Google Календарь:** задачи с `plan` или сроком со временем — событие; обратно — перенос времени.
- **Планфикс:** рабочие задачи (фильтр, например заявки и поручённые) с ролями, статусом, комментариями. Обратно:
  статус, исполнитель, комментарии.

Изменение с той стороны — событие `task_change` с `author: connector:<имя>`. Одновременная правка одного поля —
побеждает более позднее, проигравшее значение остаётся в истории задачи. Удаление там — вопрос владельцу, не
удаление здесь.

## 7. Решения проектировщика (владельцу — проверить)

1. **Итоги разбора остаются задачами** (решение 2026-11-18 «разобрать — тоже задача»): разложенное (дневник,
   план, заметка, «без дела») — задачи с признаком `filed`. Они не влияют на состояние беседы, не попадают в
   фильтры по умолчанию, процессы и зеркала.
2. **Что будет с П13:** вид «Дела», заголовки дел, `fresh_h` / `expand_last` и сворачивание сделанного в ленте
   убираются — их место занимает экран «Беседы». Вопрос «О каком деле?» остаётся под сообщением в беседе. Карточка
   «Задача выполнена?», отчёт, строка «метки / кому», подробности справа и три колонки на широком экране остаются.
3. **Человек до П7** — запись в той же базе с историей в журнале (как предложено для П7 в `decisions.md`). Ключ —
   telegram user id и номер телефона. У одного человека id в Telegram один и тот же в боте задач и в чатах BY / PL,
   поэтому эти беседы склеиваются сразу; телефоны и почта — с П7.
4. **«Ждёт меня»** считается по итогу разбора, а не по последнему сообщению. Входящее, разложенное как «без дела»
   («ок», «спасибо»), не ждёт ответа. В группе беседа ждёт меня, только если обращаются ко мне или сообщение
   относится к моей задаче. Ответ мой в любом канале беседы — ответ.
5. **«Да» на сообщения людям** — в Stream и в боте задач (кнопки «Отправить» / «Править» / «Не надо»). Если напарник
   ещё не открыл бота: при открытом окне 24 часа — бизнес-бот его чата, иначе «Открыть в Telegram» и ссылка-приглашение.
6. **Первый план** — этапы 1 и 2 вместе: модель без экранов пользы не даёт. Первый шаг плана — правка `CONCEPT.md`
   и запись в `decisions.md`. Этапы 3–7 — по одному, после недели использования предыдущего.
