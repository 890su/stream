# WhatsApp (PL) через Baileys — дизайн первого шага

> Статус: одобрен владельцем 2026-11-20. Шаг 1 — полный двусторонний канал (вариант B). Дальше (группы,
> история, статусы, номер BY) — отдельными шагами после недели использования. План — `2026-11-20-whatsapp-baileys-plan.md`.
> Уточнено при планировании (2026-11-20): LID-адреса WhatsApp, коннектор по аккаунту `whatsapp_pl`, параметры
> сокета (`markOnlineOnConnect`, `emitOwnEvents`), QR на экране «Система» через эндпоинт.

## Замысел и зачем

WhatsApp — ещё один канал владельца, его сообщения должны попадать в Stream как все остальные (голос, текст,
Telegram, звонки, SMS, Viber) и раскладываться по беседам номеров. Первым — **польский номер**.

Официальный Cloud API требует увести номер из обычного приложения, Meta Business, верификацию и помесячную
оплату (разведка 2026-11-20). Поэтому — **Baileys**: библиотека подключается как связанное устройство к
**существующему** номеру владельца (WhatsApp разрешает до 4 связанных устройств), бесплатно, без браузера.
Сообщения ложатся в беседу номера вместе со звонками, SMS и Viber. В отличие от Viber, **свои исходящие с
телефона приходят сами** через мультидевайс-синхронизацию — без чтения экрана.

## Цели

- Входящие (текст, фото, файлы, голосовые) с PL-номера → события источника `whatsapp`, в беседе номера.
- **Свои исходящие**, набранные в WhatsApp с телефона, → события «мои» (автор `me`, та же беседа).
- Ответ из ленты → отправка Baileys по номеру (коннектор `whatsapp_pl`, класс C — после подтверждения).
- Состояние канала на «Системе» (подключён / нужен вход по QR / ошибка), событие при смене.
- Привязка — один раз: владелец сканирует QR с экрана «Система» телефоном (WhatsApp → «Связанные устройства»).

## Не-цели (шаг 1)

Группы, статусы, каналы (`@g.us`, `@broadcast`, `@newsletter`); статусы доставки/прочтения и «печатает»;
подтягивание истории до привязки; правки и удаления сообщений; реакции и стикеры; номер BY (по образцу позже).
Отправка новых диалогов «вхолодную» и любые рассылки — вне продукта вообще.

## Анти-цели (провал, даже если технически работает)

- Бан номера из-за поведения: шлём **только ответы**, один номер, обычный объём (как у Viber).
- Телефон владельца перестаёт показывать уведомления WhatsApp, потому что Stream «в сети» (`markOnlineOnConnect`).
- Коннектор читает ленту или зовёт ИИ (нарушение правила 6).
- Второй процесс/вторая база/очередь без измеренной причины (правило 10).
- Состояние входа (ключи сессии) попадает в git (правило 15); содержимое сообщений — в журнал сервера.

## Ограничения

- Правило 3: новый источник — через точку расширения, без правки ядра; `decisions.md` на новое решение.
- Правило 4: пороги и имена — в `registry/whatsapp.json`, не в коде.
- Правило 10: один процесс, одна база. Baileys — в процессе Stream (как боты Telegram), не отдельным контейнером.
- Правило 14: один файл — одна задача (~300 строк), новый модуль — новым файлом, поведение покрыто тестами.
- Сервер srv-150: 1 ядро, 1,9 ГБ; Stream и стол агентов уже там. Baileys лёгкий (websocket + WebAssembly, без
  браузера и нативной сборки); тяжёлые необязательные зависимости (превью ссылок, sharp, pino) не тянем.
- Неофициально, против правил WhatsApp: сессия личного номера живёт в контейнере Stream; при бане страдает номер.
- Node 24 исполняет TypeScript напрямую; сборщика нет; проект — ESM (Baileys 7 — тоже только ESM).

## Подходы

- **A. Baileys в процессе Stream (выбрано).** Клиент `WhatsAppClient` поднимает сокет внутри `createApp` рядом с
  ботами Telegram: входящие пишет прямо в журнал через `store`, состояние — пульс, ответы — операции коннектора.
  Как Telegram (в процессе), по номеру — как Viber. Плюсы: один процесс и база, без HTTP-моста и токена, прямой
  доступ к `store`. Минус: сбой Baileys не должен ронять HTTP — изолируем (обработчики в try/catch,
  переподключение с backoff), а сам Baileys грузится только в одном файле-адаптере.
- **B. Отдельный сервис-сайдкар** (как мост Viber, но без GUI), ходит в Stream по HTTP с токеном. Отклонено: у
  Baileys нет причины для отдельного процесса, лишний процесс и токен против правила 10. Запасной путь, если
  встроенный сокет окажется нестабильным.
- **C. whatsapp-web.js (Chromium).** Отклонено: настоящий браузер на 1,9 ГБ рядом с Viber не влезет.

## Как (решённое)

Всё по образцу Telegram (`src/telegram/bot.ts` — жизненный цикл в `createApp`, `convert.ts` — чистое
преобразование с колбэками для файлов) и Viber (беседа по номеру, ответ только по номеру). Своё — адаптер Baileys.

**Адреса (LID).** С 2025 года WhatsApp может присылать адрес собеседника не номером `<n>@s.whatsapp.net`, а
анонимным `<id>@lid`. Номер берём из того из `key.remoteJid` / `key.remoteJidAlt`, что оканчивается на
`@s.whatsapp.net`; иначе — из кэша Baileys `signalRepository.lidMapping.getPNForLID`. Не нашёлся — сообщение без
номера: беседа `wa:<jid>`, автор по имени, ответ из ленты недоступен (как Viber без номера). Отправка по номеру
(`<цифры>@s.whatsapp.net`) поддерживается Baileys.

**Рантайм.** Адаптер `src/whatsapp/socket.ts` — единственный файл, который импортирует `baileys`:
`useMultiFileAuthState(<DATA_DIR>/whatsapp/<account>)`, `makeWASocket` с `markOnlineOnConnect: false`,
`emitOwnEvents: false`, `syncFullHistory: false` (недавнюю историю Baileys синхронизирует по умолчанию — ради
соответствий LID ↔ номер; в журнал она не попадает: приходит событием `messaging-history.set`, которое Stream не
слушает; уточнено 2026-11-20 по предупреждению Baileys в журнале сервера), тихим логгером без содержимого; версия протокола — `fetchLatestBaileysVersion` с запасным значением. Клиент `src/whatsapp/client.ts`
работает с адаптером через узкий интерфейс — тесты подставляют поддельный сокет. Включается флагом
`STREAM_WA_<ACCOUNT>_ENABLED=1` для аккаунтов из `registry/whatsapp.json`; выключенный канал не создаётся.

**Привязка/QR.** Baileys отдаёт QR-строку при первом старте и после отвязки. Клиент хранит последнюю; состояние
канала `login_required` с подсказкой. Экран «Система» показывает картинку из `GET /api/whatsapp/<account>/qr` (PNG,
под токеном владельца; клиент берёт её с токеном и показывает через `blob:` — CSP не пускает `data:`), обновляя
каждые 15 с. Отвязали устройство на телефоне (`loggedOut`) — ключи сессии стираются, появляется новый QR.

**Входящие (`fromMe=false`).** Чистый конвертер → событие `source: whatsapp`, `author: contact:whatsapp:<+номер
или имя>`, `kind` text/photo/file/voice, `payload.data.whatsapp = {account, chat, jid, phone?, received_at}`.
Идемпотентность — `nameId(whatsapp|<account>|in|<key.id>)` (не зависит от формы адреса). Медиа скачиваем через
адаптер и кладём `store.putMedia`; неподходящий тип/слишком большой/ошибка — текстовая пометка вместо файла.
Старше `max_age_h` (48 ч) не пишем — защита от случайной истории.

**Свои исходящие (`fromMe=true`).** Приходят сами (мультидевайс) → событие «моё»: `author: me`, та же беседа номера.
Эхо нашего же ответа из ленты не приходит (`emitOwnEvents: false`); вдобавок клиент помнит id отправленных и
пропускает их.

**Ответ из ленты.** Только по номеру: `payload.data.outbound = {connector: whatsapp_pl, chat_id: <+номер>,
chat_title}`. Клиент берёт действие (`store.actions.take`), шлёт текст на `<цифры>@s.whatsapp.net`, возвращает
результат; класс C; без повторов после сомнительной отправки (как Telegram).

**Состояние канала.** Пульс `store.status.pulse(whatsapp_pl, …)` + событие «WhatsApp PL: …» при смене.

**Контракты.** `contracts/event.schema.json`: `data.whatsapp` и `whatsapp` в известных `source`; `outbound.chat_id`
уже допускает номер. `src/contracts/whatsapp.ts` — `checkWhatsapp` (data.whatsapp только у source whatsapp; kind
text/voice/photo/file; известный аккаунт; ответ коннектору `whatsapp_*` — только по номеру); `contracts/telegram.ts`
пропускает коннекторы `whatsapp_*`.

**Реестр.** `registry/whatsapp.json` (аккаунты, лимит файла, `max_age_h`, переподключение, частота QR);
`registry/connectors.yaml` — `whatsapp_pl`; `registry/tasks.json` — тишина потока `whatsapp`.

**Клиент (по образцу Viber).** `chatOf`/`sourceKey`, `conversationOf` (номер → `tel:+…`, без номера → `wa:<jid>`),
ответ только по номеру, подписи «WhatsApp PL» и «✓ в WhatsApp», каналы в списке бесед и фильтрах, QR на «Системе».

**Зависимости.** `baileys` 7.0.0-rc14 и `qrcode` 1.5.4, точные версии.

## Безопасность и риск

Неофициально → риск бана. Снижаем: только ответы (класс C, подтверждение), один номер, обычный объём, никаких
рассылок и «холодных» диалогов. Если номер банят или отвязывают — канал отваливается, Stream работает дальше
(изоляция сокета). Содержимое сообщений в журнал сервера не пишем — только типы и id.

## Что остаётся строителю

Точный разбор редких типов сообщений Baileys сверх перечисленных; формулировки пометок о незагруженных файлах;
детали отрисовки QR на «Системе».
