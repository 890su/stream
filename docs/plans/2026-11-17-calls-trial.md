# П10 — Звонки в журнале: проба через приложение автоматизации

Концепция: `CONCEPT.md` §8.1. Решение: `decisions.md` 2026-11-17 «Звонки в журнале».

## Зачем

После звонка владелец быстро записывает, о чём был разговор и чем закончился; звонок и описание лежат в ленте
рядом и попадают в тему дела. Проба без своего приложения: неделя покажет, описываются ли звонки на деле
(правило 12). Если да — свой компаньон на Kotlin, этот приём на сервере остаётся.

## Готово, когда (проверяет владелец)

- [ ] После входящего, исходящего и пропущенного звонка в ленте появляется пузырь звонка за несколько секунд.
- [ ] Уведомление «О чём был звонок?» принимает ответ; ответ — описание под этим звонком.
- [ ] «Описать» на пузыре звонка в ленте открывает ввод продолжения звонка.
- [ ] Повтор отправки с телефона не создаёт второй звонок.
- [ ] Неделя использования; итог — в `PLAN.md`: сколько звонков, сколько описано, чего не хватило.

## Сервер

- **Контракт.** Event v1: новый `kind: call`, `source: android_calls`,
  `payload.data.call = { direction, number, name, started_at, duration_s }`; все поля, кроме `direction`,
  необязательные; `direction` ∈ `in`, `out`, `missed`, `rejected`, `unknown`. Добавление значения — без новой
  версии контракта, с записью в `decisions.md`.
- **Приём `POST /api/calls`** — простое тело (JSON или форма), удобное приложению автоматизации: `direction`,
  `number`, `name`, `ended_at` или `started_at`, `duration_s`. Сервер нормализует и пишет событие `call`.
  Идентификатор — производный UUID от номера и времени звонка (с точностью до минуты): повтор даёт тот же id и
  ответ 200. Ответ — `{ id }`, чтобы следующий запрос привязал описание.
- **Описание `POST /api/calls/:id/note`** — текст; сервер пишет обычное событие `text` с
  `payload.data.continuation = { target: <id звонка>, on: true }`. Идентификатор — от id звонка и текста.
- **Токен.** `STREAM_CALLS_TOKEN` в `/srv/stream/.env`: открывает только эти два адреса. Токен владельца в
  приложение автоматизации не кладётся.
- **Тесты:** проверка тела, повтор без дубля, чужой токен → 401, токен звонков на `/api/events` → 401,
  описание привязано к звонку, неизвестный id → 404.

## Клиент (PWA)

- Пузырь звонка: значок направления, «Входящий / Исходящий / Пропущенный», длительность, имя или номер, время.
  Номер — ссылкой `tel:`. Кнопка «Описать» → режим продолжения этого звонка в строке ввода (`composer.proceed`).
- Звонок без описания помечен; фильтр «звонки без описания» — с П2.
- Новый модуль `web/callbubble.js` (или раздел в `bubble.js`, если меньше 60 строк) — в список `VERSIONED`.

## Телефон (настраивает владелец по инструкции, агент пишет инструкцию)

Инструкция — в `deploy/CALLS.md`: шаги для Tasker и для MacroDroid. Проверить при настройке, что приложение
отдаёт на деле:
- номер и имя — обе программы отдают надёжно;
- направление и длительность — не у всех и не всегда (у Tasker отдельные переменные для исходящих, на новых
  Android значения бывают от предыдущего звонка). Если ненадёжно — читать последнюю запись журнала вызовов
  (в Tasker — запрос к `content://call_log/calls`) или слать без них: сервер примет;
- уникальный id генерировать на телефоне не нужно — его строит сервер.

Поток: «звонок завершён» → HTTP-запрос `POST /api/calls` → из ответа `id` → уведомление с полем ответа →
ответ → `POST /api/calls/:id/note`. Без сети запрос повторяется средствами приложения автоматизации; дубль
сервер отсечёт.

## Не входит

Свой компаньон на Kotlin, запись разговора, расшифровка, привязка номера к контакту (П7), вечерняя сводка
(шаг 6).
