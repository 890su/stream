# Google Календарь: синхронизация задач и занятость в «Плане» — замысел

> Статус: **утверждено владельцем** (2026-11-20: синхронизировать; задачи — из календаря «Stream»; в календаре — где исполнитель я; срок — на весь день). Решения владельца — из разговора 2026-11-20; «моё» — решения
> агента. Основа — `CONCEPT.md` §2.3 «Stream owns the tasks» (зеркала, «побеждает поздняя правка», удаление там — не
> удаление здесь) и правая панель «План» (`web/dayplan.js`).

## Зачем

В Google Календаре владельца появляются события, о которых Stream не знает (например, «отпечатки», надиктованные на
телефоне), а время, запланированное в Stream, не видно в календаре. Нужно (владелец: «синхронизировать»):
- задачи Stream со временем — в календаре, правки в календаре — обратно в задачи;
- события, созданные прямо в Google в **одном** календаре, — задачами Stream («Да, из одного календаря»);
- остальные календари (два аккаунта, «Family», «PF ИШ» и др.) — видны в «Плане» как занятость.

**Цели:** одна правда о том, когда что делается; загрузка дня видна вместе с встречами; надиктованное в календарь не
теряется. **Не цели:** Google Задачи, Todoist, Планфикс; приглашения и участники встреч; напоминания Google.
**Анти-цели:** дубли (одно дело — две задачи или два события); правка в одном месте молча теряется; задача удаляется
из-за удалённого события; содержимое событий — в журнале сервера (логи — только id и состояния).

## Подходы

1. **Вход через Google (OAuth) в своём проекте Google Cloud** — выбран (владелец: «синхронизировать» — нужна запись).
   Оба аккаунта, чтение и запись, тот же вход позже — для контактов Google (П7, этап 2).
2. Секретная ссылка iCal — только чтение, с задержкой; запись невозможна.
3. Сервисный аккаунт с расшаренными календарями — тоже нужен проект Google Cloud и ручная расшарка каждого календаря.

## Как устроено

**Подключение (один раз, владелец).** Проект в Google Cloud: включить Google Calendar API; экран согласия — внешний,
статус «В работе» (иначе вход истекает через 7 дней; приложение не проверено Google — при входе «Дополнительно →
перейти», это нормально для личного приложения); OAuth-клиент «Веб-приложение» с адресом возврата
`https://stream.sekond.pl/api/google/callback`. ID и секрет клиента — две строки в `/srv/stream/.env`
(`STREAM_GOOGLE_CLIENT_ID`, `STREAM_GOOGLE_CLIENT_SECRET`); агент даёт пошаговую инструкцию в `deploy/GOOGLE.md`. На
экране «Система» — «Подключить Google»: вход в каждый аккаунт (iharshastsiuk, iharszasciuk). Ключи доступа (refresh
token) — в томе данных `/srv/stream/data/google/<аккаунт>.json`, не в git и не в журнале. Права — только календарь.

**Коннектор** — в процессе сервера, как боты Telegram и WhatsApp (моё): опрос раз в `poll_s` (60 с) с `syncToken` по
каждому календарю; состояние канала на «Системе» (работает / нужен вход / ошибка), события «Google: …» в ленте при
смене. Без новых зависимостей — запросы к API через `fetch` (моё).

**Календарь «Stream»** создаётся коннектором в аккаунте, выбранном на «Системе» (по умолчанию — первый подключённый;
моё). Связь задачи и события — в самом событии (`extendedProperties.private.stream_task = <id задачи>`), поэтому
журнал не засоряется служебными записями (моё).

| Где изменили | Что происходит |
|---|---|
| Stream: у моей задачи появилось «Когда» (план) или срок | событие в «Stream» (со временем — по «Когда», на весь день — по сроку), название = название задачи, описание = описание задачи + ссылка на неё |
| Stream: «Когда» изменили / убрали | событие сдвигается / удаляется |
| Stream: название | название события |
| Stream: задача закрыта | событие остаётся, название с «✓ » в начале |
| Stream: задача отменена | событие удаляется |
| Google: событие в «Stream» сдвинули или растянули | у задачи меняются начало и длительность |
| Google: переименовали | меняется название задачи |
| Google: удалили событие | у задачи снимается «Когда»; задача остаётся (не удаление — CONCEPT §2.3) |
| Google: **создали** событие в «Stream» | новая задача владельца (`todo`, исполнитель — я) с этим временем, названием и описанием; событие получает `stream_task` |
| Google: событие на весь день в «Stream» | задача со сроком этим днём, без «Когда» |

Правки из Google пишутся как `task_change` автора `system` с пометкой коннектора (моё: `processor: google-calendar`).
Конфликт — побеждает более поздняя правка (`updated` события против `updatedAt` задачи); проигравшее значение остаётся
в истории задачи. Эхо своих же изменений гасится сравнением значений: равные — ничего не пишется.

**Уточнения по проверке замысла (моё):**
- **Какие задачи — в «Stream»:** задачи, где **исполнитель — я** (владелец 2026-11-20: «я исполнитель — эти задачи в
  календаре»), открытые и не подшитые, с «Когда»; включая «разобрать», «жду» и «отложено». Где я только
  ответственный, контролёр или наблюдатель — не в календаре. При подключении — только с «Когда» от
  сегодняшнего дня; прошлые и закрытые до подключения не переносятся. Задача, закрытая после, остаётся событием с «✓».
- **Чьи правки из Google:** календарь «Stream» правит только владелец, поэтому правки оттуда — автора `me` с пометкой
  `processor: google-calendar`; название, заданное в Google, — названное владельцем (разбор и именование его не
  трогают). Задача из нового события — тоже владельца.
- **Срок** (владелец 2026-11-20: «да, на весь день»): моя задача без «Когда», но со сроком — событие на весь день в
  день срока (срок со временем — тоже на весь день этого дня). Связь в обе стороны: перенёс событие на другой день —
  меняется срок; удалил — срок снимается (с записью в ленте, как ниже). Появилось «Когда» — то же событие становится
  событием со временем, убрали «Когда» — снова на весь день по сроку; дублей нет. Событие на весь день, созданное в
  «Stream», — задача с этим сроком.
- **Удаление события в Google:** у задачи снимается «Когда», а в ленту пишется служебная запись «Google: событие
  удалено — у задачи «…» снято время» с переходом к задаче. Отступление от CONCEPT §2.3 («вопрос владельцу»): удаление
  в своём календаре — осознанное действие, вопрос лишний; запись в ленте оставляет след и даёт вернуть время.
- **Описание:** в обе стороны — описание задачи ⇄ описание события; ниже черты — ссылка на задачу
  `https://stream.sekond.pl/?task=<id>` (новый вход в приложение сразу в карточку), при возврате из Google она
  отрезается.
- **Как пишется в Google:** цикл сверки в коннекторе, а не действия в очереди: в томе данных хранится «последнее
  согласованное» по каждой связке задача–событие (время, название, описание, `etag`). Изменилось только в Stream —
  отправить; только в Google — записать в задачу; в обоих — побеждает более поздняя правка (по истории задачи и
  `updated` события). Неудавшаяся отправка не теряется: базис не обновлён — следующий круг повторит. Ошибки — в
  состоянии канала на «Системе».
- **Адрес возврата входа** `/api/google/callback` — без токена владельца, защищён подписанным `state`; ссылку на вход
  «Подключить Google» выдаёт запрос с токеном.

**Остальные календари** обоих аккаунтов (кроме «Stream» и праздников; моё) — только чтение: события на окно
`window_days` (14) — в памяти сервера, отдаются клиенту (`/api/calendar?from&to`). «План» показывает их серыми
строками среди задач дня с временем и названием календаря; касание — открыть событие в Google. Какие календари
показывать — переключатели на «Системе» (моё); выбор хранится в томе данных.

**Повторяющиеся события:** в «Плане» — каждым разом; в «Stream» повторяющееся событие задачей не становится (только
видно в «Плане») — моё, чтобы не плодить задачи. Задача с повтором — событие только у текущего раза; следующий раз
получит своё событие, когда появится его «Когда».

## Этапы

1. **Вход и занятость:** OAuth, «Подключить Google» на «Системе», чтение календарей, серые события в «Плане».
2. **Синхронизация «Stream»:** календарь «Stream», задачи со временем ⇄ события, новые события → задачи.

Каждый этап выкладывается отдельно; этап 1 полезен сразу (видна реальная загрузка).

## Оставлено исполнителю

Формат `registry/google.json` (`poll_s`, `window_days`, имя календаря «Stream»); вид серых строк в «Плане»; тексты
«Системы» и инструкции; ограничение частоты запросов к API и повтор при ошибке (backoff, как у WhatsApp).
