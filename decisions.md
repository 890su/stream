# Decisions: Stream

> Key decisions made during work. Appended as they happen.

## 2026-11-10 — Основа: неизменяемый журнал событий
**What:** Всё входящее сохраняется как событие и никогда не меняется. Над журналом — пересчитываемые слои:
нормализация, интерпретация (с версиями), действие. Исправление — новое событие и новая версия.
**Why:** Можно вернуться к источнику от любой задачи или расхода; можно перезапустить обработку новой моделью;
ошибка ИИ ничего не портит.
**Boundary:** Нет UPDATE/DELETE для событий. Удаление персональных данных по требованию — отдельное решение,
когда понадобится.
**Affected:** `CONCEPT.md` §2, `contracts/event.schema.json`

## 2026-11-10 — Развитие только через четыре точки расширения
**What:** Источник, цель, коннектор, автоматизация. Цели, поля, пороги и шаблоны — данные в `registry/`.
**Why:** Не скатиться в костыли под частные случаи; ИИ-аналитик может предлагать правки реестра, а не кода.
**Boundary:** Что не ложится в четыре точки — изменение ядра с записью здесь.
**Affected:** `CONCEPT.md` §2.1, `registry/`

## 2026-11-10 — Уверенность × класс риска решают, что делать самому
**What:** Классы A (внутреннее), B (черновик наружу), C (необратимое наружу) и пороги 0,85 / 0,6. Уверенность
по цели считается по истории принятых без правок разборов.
**Why:** Самооценка модели откалибрована плохо; наружу ничего не уходит без «да».
**Affected:** `CONCEPT.md` §3.1, `registry/intents/*.yaml`

## 2026-11-10 — ИИ: дешёвая модель по API для потока, подписки для тяжёлого
**What:** Поток — Haiku или Gemini Flash-Lite по API с лимитом трат. Тяжёлое — `claude -p`, `codex exec`,
`grok -p` по подпискам владельца. Kimi — только для кода. Всё за `interpret()`.
**Why:** Поток стоит единицы долларов в месяц; подписки не упираются в него пятичасовыми окнами; правила
подписок менялись в 2026 году дважды — провайдер должен меняться настройкой.
**Affected:** `CONCEPT.md` §6

## 2026-11-11 — Ввод в своём приложении, не в Telegram
**What:** Ввод голосом, текстом и фото — в своём PWA на Android, плюс «Поделиться» и офлайн-очередь.
Telegram остаётся будущим источником переписки с клиентами.
**Why:** Одно приложение для ввода, ленты и задач; не зависеть от тем в личных чатах Telegram-ботов.
**Boundary:** Ввод должен быть не медленнее мессенджера — до записи не больше двух касаний.
**Affected:** `CONCEPT.md` §5

## 2026-11-11 — Встроенный менеджер задач; Todoist и TickTick — резервные коннекторы
**What:** Задачи — проекция ленты внутри системы. Внешние менеджеры — зеркала через коннекторы.
**Why:** Нет синхронизации и конфликтов; задача видна в теме рядом с исходником, перепиской и расходами.
**Boundary:** Минимальный набор функций (`CONCEPT.md` §2.3). Новая функция задач — только если её не закрывает
коннектор к Todoist.
**Affected:** `CONCEPT.md` §2.3, `contracts/task.schema.json`, `registry/connectors.yaml`

## 2026-11-11 — Стек: Node 24 + TypeScript без сборки, встроенный SQLite
**What:** Node 24 запускает TypeScript напрямую (снятие типов); база — `node:sqlite`, один файл
`data/stream.db`; HTTP — `node:http`; клиент `web/` — обычный JavaScript без фреймворка и сборщика.
Зависимостей для работы нет; для разработки — `typescript` и `@types/node` (проверка типов). Тесты —
`node --test`. Менеджер пакетов — pnpm. Команды: `pnpm start`, `pnpm test`, `pnpm typecheck`.
**Why:** Один стек с собственными проектами, одна команда запуска, нет сервера базы и сборки, тесты идут
доли секунды. Нагрузка — один пользователь.
**Boundary:** `node:sqlite` в Node 24 экспериментальный — вся работа с базой только в `src/store/`, хранилище
заменяемо без правок остального кода. TypeScript — только стираемый синтаксис (`erasableSyntaxOnly`: без
`enum`, `namespace`, параметров-свойств). Python/FastAPI + PostgreSQL (как прежний учёт времени) остаётся
запасной альтернативой: переход — новая запись здесь; контракты, реестр и API от стека не зависят.
**Affected:** `docs/plans/2026-11-11-step1-journal-capture.md`, `src/`, `web/`, `test/`, `package.json`

## 2026-11-11 — iCRM: не связываем сейчас; позже — отдельный коннектор
**What:** Лента — самостоятельный проект. iCRM на этапе MVP никак не связана с лентой: ни общего кода, ни
общей базы. Позже iCRM подключается как обычный коннектор (заявки, оплаты, клиенты) по контракту Action —
наравне с Планфиксом.
**Why:** У ленты своя основа (неизменяемый журнал, версии разбора, уверенность), у iCRM — изменяемые
экземпляры с полями. Решение владельца: связь — позже и только через коннектор.
**Boundary:** Не импортировать код iCRM и не обращаться к её базе. Стек совпадает, но общие части не
выносятся в библиотеку, пока не встретятся трижды (правило трёх).
**Affected:** `CONCEPT.md` §7, §11, `registry/connectors.yaml` (`icrm: later`)

## 2026-11-11 — Сервер и HTTPS: srv-150 за Cloudflare Tunnel
**What:** Сервер работает на srv-150 (домашняя ESXi VM, где уже стоят n8n и cloudflared). Наружу —
через существующий Cloudflare Tunnel на поддомене `stream.sekond.pl`; HTTPS даёт Cloudflare, на сервере
порт слушает только `127.0.0.1`. Запуск — Docker Compose (`node:24-slim`, без зависимостей) или systemd —
выбирает шаг развёртывания. Код разворачивается `git clone` из GitHub в каталог вне зеркала Google Drive
(`~/services/stream`); база и медиа — в `~/services/stream/data`, с ночной копией. Разработка — `localhost`
на ПК.
**Why:** Инфраструктура уже есть и работает (туннель, домен, Docker); ничего не стоит; не нужен открытый
порт и свой сертификат. `~/aibrain` на сервере — зеркало Drive, его синхронизация может затереть правки
и базу, поэтому код и данные живут отдельно.
**Boundary:** Доступ — один владелец по длинному токену `STREAM_OWNER_TOKEN` (`Authorization: Bearer`);
Cloudflare Access не ставится: его редирект на вход ломает фоновую отправку очереди и «Поделиться» в PWA.
Таймаут прокси Cloudflare — 100 с; медиа грузятся отдельными `PUT` и в него укладываются. Если домашний
интернет или srv-150 окажутся ненадёжны за неделю использования — переезд на VPS (`srv-vpsag`) той же
командой, новая запись здесь.
**Affected:** `docs/plans/2026-11-11-step1-journal-capture.md` («Развёртывание»), `CONTEXT.md`
(«Deployment»)

## 2026-11-11 — Детали шага 1, идемпотентность и курсор хронологии

**What** — Хеш события считается по рекурсивно отсортированному JSON, с `reply_to` и `topic_hint`,
нормализованными в `null`. `received_at` устанавливает сервер, это поле исключено из хеша входного тела.
В транзакции записи сервер выбирает время не меньше предыдущего `received_at` плюс одна миллисекунда.
Время хранится в UTC с миллисекундами и уникально. Ответ списка содержит `events` и `next_before`.

**Why** — Повтор с другим порядком ключей имеет тот же результат. Строгий курсор `before` проходит
события, принятые в одну миллисекунду, с сохранением полного порядка.

**Boundary** — Контракт Event v1 сохраняется. Клиентский `ts` хранится исходным. При высокой скорости
ввода `received_at` может на несколько миллисекунд опережать настенные часы. Изменение тела с тем же id даёт 409.

**Affected** — `src/store/`, `src/server/events.ts`, `test/store.test.ts`, `test/api.test.ts`.

## 2026-11-11 — Комплект развёртывания шага 1 через пользовательский systemd

**What** — Подготовлены пользовательские units `stream.service`, `stream-backup.service` и
`stream-backup.timer`. Ночная копия через `VACUUM INTO` включает базу и медиа, на которые ссылается снимок.
Копии сохраняются в датированных каталогах `~/backups/stream`.

**Why** — Node 24 запускает сервер напрямую. systemd поддерживает перезапуск и ночной таймер.
Тест восстановления проверяет согласованность базы и медиа.

**Boundary** — Выкладку и маршрут существующего Cloudflare Tunnel применяет владелец по `deploy/DEPLOY.md`.
Проверки Android и неделя использования остаются открытыми. Хранение и перенос резервных копий контролирует владелец.

**Affected** — `deploy/`, `src/backup.ts`, `src/store/store.ts`, `PLAN.md`.

## 2026-11-11 — Развёртывание: отдельный контейнер и пользователь на srv-150 (заменяет systemd-комплект)
**What:** Stream работает на srv-150 (сейчас `192.168.0.149`) в своём compose-проекте `stream`: системный
пользователь `stream` без входа, каталог `/srv/stream` (`app`, `data`, `backups`, `.env`), контейнер
`node:24-slim` без прав (`cap_drop: ALL`, только чтение, 256 МБ, 0,5 CPU), порт `127.0.0.1:3790`. Ночная копия —
системный таймер, хранение 30 дней. Установка и обновление — `sudo bash deploy/install.sh [ref]`, он же
добавляет правило в локальный конфиг Cloudflare Tunnel.
**Why:** Владелец просил отделить Stream от остальных проектов; на хосте Node 18, а нужен 24 — контейнер не
трогает систему. Синхронизация Google Drive на сервере выключена владельцем (таймер `sync-aibrain`).
**Boundary:** Шаги с root (пользователь, `/srv`, unit-файлы, конфиг туннеля) выполняет владелец: sudo на
сервере требует пароль. Сервер слушает `HOST` (по умолчанию `127.0.0.1`; в контейнере `0.0.0.0`).
**Affected:** `deploy/`, `.dockerignore`, `src/main.ts`, `.env.example`

## 2026-11-11 — Один экран-чат вместо вкладок «Записать» / «Лента»; метки при вводе
**What:** Клиент — один экран по образцу мобильного мессенджера: прокручиваемая лента пузырей (новые внизу)
и строка ввода с кнопкой меток слева, скрепкой и кнопкой голоса / «Отправить» справа. Метки, выбранные
владельцем, пишутся в событие необязательным полем `payload.tags` (шаблон `^#[\p{L}0-9_-]+$`); быстрый набор
меток — `quick_tags` в `registry/capture.json`.
**Why:** Решение владельца: две вкладки не нужны, привычный вид чата быстрее. Метки владельца — дешёвая и
точная подсказка для будущего `interpret()`.
**Boundary:** `payload.tags` добавлено в Event v1 без смены версии: поле необязательное, старые события
валидны, читатели его могут игнорировать. Окончательные теги события — в Interpretation; `payload.tags` —
только исходник. Внешний вид — общий шаблон чата, без чужих логотипов и фирменных элементов.
**Affected:** `CONCEPT.md` §5, `contracts/event.schema.json`, `src/contracts/validate.ts`,
`registry/capture.json`, `web/`

## 2026-11-11 — Файлы клиента по адресу сборки `/v/<build>/`; страница из сети в первую очередь
**What:** Сервер считает номер сборки (хеш файлов `web/` и `registry/capture.json`) и отдаёт файлы клиента
только по `/v/<build>/<file>` с `immutable`; `/` и `/sw.js` — `no-cache`, номер подставляется в них.
Сервис-воркер берёт страницу и настройки из сети (таймаут 4 с, иначе кеш), файлы сборки — из своего кеша,
обновляется сразу (`skipWaiting`, `updateViaCache: 'none'`, проверка при возврате в приложение) и
перезагружает страницу, если нет записи и черновика.
**Why:** Cloudflare подменял `no-cache` у `.js` и `.css` на `max-age=14400`: телефон брал новую страницу со
старыми скриптами и стилями — интерфейс смешивался. Адрес по сборке не зависит от настроек CDN.
**Boundary:** Список `VERSIONED` в `src/server/static.ts` и `web/sw.js` должен совпадать с файлами `web/` —
это проверяет тест. Старая сборка по своему адресу больше не отдаётся (404).
**Affected:** `src/server/static.ts`, `src/server/http.ts`, `web/sw.js`, `web/index.html`, `web/app.js`,
`test/shell.test.ts`

## 2026-11-11 — Мгновенная синхронизация клиентов: Server-Sent Events
**What:** `GET /api/live` держит поток SSE; сервер при записи нового события (API или «Поделиться») сразу шлёт
его всем открытым клиентам. Клиент читает поток через `fetch` с `Authorization: Bearer`, переподключается с
нарастающей паузой (1–30 с), в фоне соединение закрывает, при возврате переподключается и догружает ленту.
Опрос раз в 30 с остаётся только запасным путём, пока поток не подключён.
**Why:** Владелец пишет с телефона и компьютера и хочет видеть одно и то же без перезагрузки. SSE — один
процесс, без очередей и библиотек (правило 10); нагрузка — одно тихое соединение на открытый клиент.
**Boundary:** `EventSource` не используется: не умеет заголовки, а токен в адресе попал бы в логи прокси.
Пинг каждые 25 с — из-за таймаута Cloudflare 100 с. Оповещение — внутри процесса; второй процесс сервера
потребовал бы общей шины (сейчас не нужен).
**Affected:** `src/server/live.ts`, `src/server/http.ts`, `src/server/events.ts`, `src/server/share.ts`,
`web/live.js`, `web/feed.js`, `web/app.js`, `test/live.test.ts`

## 2026-11-11 — Правка, архив и удаление — события-правки поверх неизменяемого журнала
**What:** Ответ — сообщение с `reply_to`. Изменить, в архив / вернуть, удалить / восстановить — событие
`kind: correction` с `payload.ref = {type: event, id}` и `payload.data.op` из `edit | archive | unarchive |
delete | restore`; для `edit` — новые `text` и `tags`. Лента — проекция: последняя правка по времени побеждает.
Сервер принимает правку, только если исходное событие уже в журнале и само не является правкой (иначе 422 / 400).
Очередь на телефоне отправляет записи по времени создания, чтобы правка не ушла раньше исходника.
**Why:** Владельцу нужны привычные действия мессенджера, а журнал не меняется (правило 1). Последствия правки
для разбора, действий, коннекторов и автоматизаций описаны таблицей в `CONCEPT.md` §2.4 и включаются с шага 3.
**Boundary:** «Удалить» — отзыв, не стирание. Медиа не правятся. Контракт Event остаётся v1: `correction` уже
был в списке `kind`, правила `data.op` проверяет `src/contracts/correction.ts`. Компенсирующие действия и
`undo/update/irreversible` у коннекторов — проектные правила на шаг 3+, кода пока нет.
**Affected:** `CONCEPT.md` §2.4, §5, `src/contracts/correction.ts`, `src/store/store.ts`, `web/projection.js`,
`web/actions.js`, `web/composer.js`, `web/bubble.js`, `web/feed.js`
